ANDROID ROBOT VISUALIZATION APP — COMPLETE DEVELOPMENT SPECIFICATION

1. PURPOSE

Build a production-quality Android application that acts as a real-time visual representation of an industrial robot controlled by an MCU over Bluetooth Low Energy (BLE).

The Android application is primarily a visualization and animation system.

The MCU is the source of truth for the robot's actual operation, sequencing, module states, movement events, and timing.

The Android app must NOT independently control the physical robot's movement or sequencing.

The Android app listens to the MCU's BLE messages and accurately reproduces the corresponding material-transfer operations visually.

--------------------------------------------------
2. SYSTEM ARCHITECTURE
--------------------------------------------------

The architecture is:

MCU
 |
 | BLE UART
 |
 v
Android App
 |
 +-- BLE listener
 +-- Protocol parser
 +-- Module visualization
 +-- Robot animation
 +-- Coordinate storage
 +-- Calibration UI
 +-- Status display

The MCU controls the actual robot/process.

The Android app visualizes what the MCU is doing.

The Android app does not send coordinates to the MCU.

The MCU only communicates module/slot numbers and event cues.

--------------------------------------------------
3. BLE COMMUNICATION PROTOCOL
--------------------------------------------------

The MCU communicates with the Android application through a BLE module connected to its UART.

Every message is plain ASCII text terminated with:

\n

The MCU currently sends ONLY these messages:

READY
SEQ:<n>
RUN:<slot>
DONE:<slot>
MOVE:<a>><b>
LOT:DONE

There is currently NO Android-to-MCU communication.

The MCU is transmit-only.

Do not invent additional MCU commands.

--------------------------------------------------
4. BLE MESSAGE MEANINGS
--------------------------------------------------

READY

Indicates that the MCU/controller has powered up and is idle.

Example:

READY

Android should transition to the ready/idle state.


SEQ:<n>

Indicates that a new sequence has started.

Example:

SEQ:1

Android should visually indicate that sequence 1 has started.


RUN:<slot>

Indicates that a module has started its processing/run phase.

Example:

RUN:3

The corresponding module must become visually active/yellow.

The module remains yellow until the corresponding DONE:<slot> event is received.


DONE:<slot>

Indicates that the specified module has completed its run.

Example:

DONE:3

Android should remove the yellow/active state and transition the module to its appropriate completed/inactive visual state.


MOVE:<a>><b>

This represents a physical robot material-transfer operation.

Example:

MOVE:2>6

This means material is being transferred from Module 2 to Module 6.

Android must:

1. Identify Module 2.
2. Identify Module 6.
3. Retrieve their calibrated visual positions.
4. Animate the industrial robot from Module 2 to Module 6.
5. Visually represent the material being picked up.
6. Visually represent the material being transported.
7. Visually represent the material being deposited.
8. Complete the robot animation.
9. Return the robot to the appropriate idle state.

The MCU sends ONLY the module numbers.

The MCU never sends coordinates.


LOT:DONE

Indicates that the entire lot has finished/shipped.

Example:

LOT:DONE

Android should display an appropriate final/completed state.

--------------------------------------------------
6. MODULE COORDINATES / CALIBRATION
--------------------------------------------------

Android owns all visual module positions.

The MCU does NOT know the module coordinates.

The MCU does NOT send coordinates.

The Android application must have a calibration mode.

The user must be able to select a module and tap on the arena/map to define that module's visual position.

Example:

Select Module 1
Tap desired location
Module 1 position is saved

Select Module 2
Tap desired location
Module 2 position is saved

Continue until all required modules have been positioned.

The positions must persist after closing and reopening the app.

Do NOT permanently store raw screen pixel coordinates.

Use normalized/logical coordinates instead.

For example:

x = 0.0 to 1.0
y = 0.0 to 1.0

The app converts these logical coordinates to actual screen coordinates when rendering.

This ensures the module positions remain correct across different screen resolutions and aspect ratios.

--------------------------------------------------
7. PACKAGING / BOTTLING
--------------------------------------------------

Packaging/Bottling is a special station and does not need to be treated as one of the 9 manually calibrated modules unless explicitly configured later.

Do not invent a new slot number for Packaging/Bottling.

Keep the implementation extensible enough to support a predefined fixed position for special stations if needed.

8. ROBOT VISUALIZATION
--------------------------------------------------

The robot must look like a detailed 4-axis industrial robotic arm based on the reference image provided separately.

Do NOT use a simple robot icon.

The robot should look like a real industrial machine.

It should include detailed mechanical components such as:

- Robot base
- Bearings
- Rotary joints
- Arm segments
- Shafts
- Joint housings
- Linkages

The robot should have a very high level of visual detail.

The purpose is to make the demonstration visually impressive and understandable to an audience.

However, visual detail must not cause severe performance problems.

--------------------------------------------------
9. ROBOT RAIL
--------------------------------------------------

The robot operates on a linear rail running through the middle of the application's arena.

The rail must be clearly visible.

The robot is mounted on a carriage attached to the rail.

The rail should visually resemble an industrial screw-driven linear axis.

Include visual details such as:

- Rail body
- Lead screw
- Carriage
- Mechanical supports
- Robot mounting plate
- Bearings or screw supports

The robot must remain physically attached to the rail.

It must NOT teleport between modules.

--------------------------------------------------
11. ANIMATION SPEED
--------------------------------------------------

The robot movement should be deliberately slow enough for an audience to clearly understand what is happening.

Do not optimize purely for speed.

The animation should clearly show:

- Source module
- Destination module
- Robot travelling along the rail
- Robot positioning itself
- Arm movement
- End effector movement
- Material pickup
- Material transportation
- Material placement
- Completion of the transfer

Every joint movement should be visible.

Use smooth interpolation/easing.

Avoid instantaneous position changes.

The current firmware has a conceptual robot-transfer animation time of approximately 4000 ms, but the Android implementation should make this configurable so the animation can be tuned later.

--------------------------------------------------
12. MODULE STATE VISUALIZATION
--------------------------------------------------

The Android application must synchronize module states with MCU events.

When:

RUN:<slot>

is received:

The corresponding module becomes YELLOW/ACTIVE.

Example:

RUN:4

Module 4 becomes yellow.

Module 4 remains yellow until:

DONE:4

is received.

After DONE:4, Module 4 transitions to its appropriate completed/inactive state.

Android must not independently invent module states.

The MCU is the source of truth.

--------------------------------------------------
13. SYNCHRONIZATION
--------------------------------------------------

Synchronization with the MCU is extremely important.

Android must react to the MCU's events.

Android must NOT create an independent process/sequence engine that tries to predict what the MCU will do.

Example:

READY
SEQ:1
RUN:3
DONE:3
MOVE:3>7
RUN:7
DONE:7
LOT:DONE

The Android app should visually reproduce this sequence.

The MCU determines the actual order and timing of events.

--------------------------------------------------
14. ROBOT TRANSFERS VS NORMAL SWIPES
--------------------------------------------------

This distinction is extremely important.

Not every material movement represents a physical robot transfer.

Only actual robot-transfer operations should cause the industrial robot animation.

Normal process/swipe operations such as:

blender -> vessel
vessel -> packaging/bottling
exit

do NOT represent a physical robot-arm transfer.

Do not invent robot movement for these operations.

The Android app must reproduce what the MCU actually communicates.

--------------------------------------------------
15. CURRENT MCU COMMUNICATION DIRECTION
--------------------------------------------------

Current communication:

MCU --------------------> Android

The MCU is transmit-only.

There is currently no:

Android -----------------> MCU

communication.

Do not implement fake acknowledgements.

Do not pretend the MCU has received anything from Android.

--------------------------------------------------
19. BLE PARSING
--------------------------------------------------

BLE data cannot be assumed to arrive as complete messages.

Implement a proper text buffer.

Messages are terminated by newline:

\n

For example, BLE could deliver:

MOV
E:2>6\n

The parser must reconstruct:

MOVE:2>6

before processing it.

BLE may also deliver multiple messages together:

RUN:2\nDONE:2\nMOVE:2>6\n

The application must correctly split and process each message independently.

Handle:

- Fragmented messages
- Multiple messages
- Empty lines
- Unexpected whitespace where appropriate
- Unknown messages
- Malformed messages
- Disconnects
- Reconnects

The application must never crash because of malformed BLE input.

--------------------------------------------------
20. UNKNOWN / INVALID MESSAGES

Unknown messages should be safely ignored or logged.

Examples:

MOVE:2
RUN:
INVALID DATA

The application must remain stable.

A developer/debug log showing raw BLE messages is recommended.

If another MOVE event arrives while the robot is already performing a transfer, handle it deterministically.

Do not start multiple robot animations simultaneously.

The behavior must be documented in the code.

THE MCU CONTROLS THE ROBOT.
ANDROID VISUALIZES THE ROBOT.

The MCU is the source of truth.

Android uses the 9 calibrated module positions to determine where the robot should visually travel.

The MCU only sends module numbers and event cues.

The final result should feel like a professional industrial automation demonstrator, with a highly detailed 4-axis industrial robot moving along a central screw-driven rail and performing clear, slow, synchronized material-transfer animations in response to the real MCU firmware.

IMPORTANT VISUALIZATION CHANGE:

THE 9 PHYSICAL MODULES ARE OUTSIDE THE ANDROID DISPLAY.

DO NOT RENDER THE MODULES THEMSELVES ON THE ANDROID SCREEN.

The Android screen represents the robot's workspace and the robot itself.

The real physical modules/stations exist outside the displayed workspace, around the physical robot.

Therefore, the Android visualization should NOT show nine module boxes or nine module icons inside the application.

Instead, each module has a calibrated visual interaction point associated with an edge of the Android workspace.

For example:

Module 1 -> top/left/right/bottom edge position
Module 2 -> top/left/right/bottom edge position
...
Module 9 -> corresponding edge position

These positions represent where the real physical module is located relative to the robot.

When the MCU sends:

MOVE:2>6

Android should:

1. Look up the calibrated interaction position for Module 2.
2. Move the robot/rail carriage toward the appropriate position.
3. Move the robot arm toward the edge of the display corresponding to Module 2.
4. Visually extend the robot arm toward and partially beyond the edge of the visible workspace.
5. Animate the material pickup from the physical module located outside the display.
6. Retract the arm.
7. Move the robot along the rail toward the destination position for Module 6.
8. Extend the arm toward the corresponding edge for Module 6.
9. Visually extend/reach beyond the display boundary to represent placing material into the physical Module 6.
10. Retract the arm.
11. Return to the appropriate idle position.

The modules themselves must remain invisible.

The edge of the screen represents the boundary between the Android visualization and the real physical environment.

The robot should therefore appear to physically reach OUT OF the displayed workspace toward the real-world module.

--------------------------------------------------
MODULE CALIBRATION
--------------------------------------------------

Calibration should therefore NOT mean placing visible module icons on the screen.

Instead, calibration defines the exact point on the Android workspace where the robot should reach when interacting with each physical module.

For example:

Module 1:
edge = LEFT
position = 0.25 along left edge

Module 2:
edge = TOP
position = 0.60 along top edge

Module 3:
edge = RIGHT
position = 0.40 along right edge

etc.

The calibration UI should allow the user to select:

Module 1
Module 2
...
Module 9

and then tap a point near/on the edge of the workspace to define the robot's interaction point.

The selected calibration point should be visible while calibrating, but the module itself should NOT be drawn.

The calibration point represents the physical location of the external module relative to the robot.

--------------------------------------------------
EDGE INTERACTION
--------------------------------------------------

The robot must NOT simply stop at the edge.

The arm itself should visibly extend toward the edge.

For example:

             EDGE OF DISPLAY
                    ↓
        ┌──────────────────────┐
        │              \       │
        │               \      │
        │                \     │
        │                 🤖───┼──→ OUTSIDE
        │                      │
        │════════ RAIL ════════│
        └──────────────────────┘

The end effector may partially disappear beyond the display boundary.

This is intentional.

It should look as though the robot is physically reaching toward a real module that is located outside the Android visualization.

--------------------------------------------------
NO MODULE UI
--------------------------------------------------

Do NOT display:

- Module boxes
- Module icons
- Module containers
- Fake physical modules
- Nine stations arranged around the screen
- Module machinery inside the app

The only indication of a module during normal operation should be through the robot's movement and optionally a small status indicator/text such as:

"TRANSFERRING: MODULE 2 → MODULE 6"

The physical modules are represented by the real-world hardware, not by graphics inside the Android app.

--------------------------------------------------
COORDINATE SYSTEM
--------------------------------------------------

Because the modules are outside the displayed workspace, module coordinates should represent ROBOT INTERACTION POINTS rather than module positions.

Use normalized coordinates:

X = 0.0 ... 1.0
Y = 0.0 ... 1.0

or an equivalent edge-coordinate representation.

The calibration data should determine where the robot needs to position its carriage and how far/where the arm needs to reach toward the display boundary.

The implementation must keep the coordinate system resolution-independent.

--------------------------------------------------
ROBOT VISUALIZATION PRINCIPLE
--------------------------------------------------

The Android screen is essentially a "window" into the robot's working area.

The real physical modules are outside that window.

The animation should make this relationship obvious.

The robot should appear to:

- Travel along the central rail.
- Position itself relative to the external module.
- Reach toward the appropriate screen edge.
- Extend its arm beyond the visible workspace.
- Interact with the external module.
- Retract.
- Travel to the next external module.
- Reach beyond the corresponding edge.
- Complete the transfer.

This is more important than displaying the modules themselves.

The goal is for an audience watching the Android display to understand:

"THE ROBOT IS REACHING OUTSIDE THE SCREEN TO THE REAL PHYSICAL MODULE."

Do not compromise this concept by placing virtual modules inside the application.
